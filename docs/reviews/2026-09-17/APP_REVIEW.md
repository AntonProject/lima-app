## P1 — исправить до релиза

### R07. Очереди одного аккаунта доступны после входа в другой

Код: [очистка данных](</Users/a123/a123-dev/lima/lib/core/db/local_database.dart:2051>), [смена владельца](</Users/a123/a123-dev/lima/lib/features/auth/data/auth_repository_impl.dart:128>), [отправка организаций](</Users/a123/a123-dev/lima/lib/core/services/pending_mutation_sync_service.dart:265>).

`clearUserScopedData()` вызывается при смене логина, но не очищает и не изолирует `pending_plans` и `pending_organizations`. Их чтение не фильтруется по владельцу. После входа B очередь A остаётся доступной обработчику, использующему текущую сессию B. Одновременно очистка удаляет `visits`, включая несинхронизированные записи A. Простое добавление оставшихся очередей в список удаления устранит смешение, но уничтожит pending-данные.

Тест R07: у A создано по одной записи в двух очередях; после штатной очистки и установки владельца B оба чтения возвращают по одной чужой записи вместо нуля. Исправление: хранить владельца у всех локальных действий, читать/отправлять только его очередь и сохранять неотправленные действия прежнего пользователя изолированно.

### R01. Рассчитанная цена подменяется каталожной перед отправкой

Код: [слияние каталога](</Users/a123/a123-dev/lima/lib/features/visits/presentation/view_models/pharmacy_order_view_model.dart:509>), [пропуск повторного расчёта](</Users/a123/a123-dev/lima/lib/features/visits/presentation/view_models/pharmacy_order_view_model.dart:349>).

Экран подбора передаёт в подтверждение цены из расчёта. Затем `load()` вызывает `_mergeDrug()`, где положительная каталожная цена безусловно заменяет цену выбранной строки. Если `marginId` уже выбран, отправка считает эти значения рассчитанными и не пересчитывает их.

Тест R01: исходная рассчитанная цена 130, локальный каталог 100; в отправленном заказе получается 100 при `pricesAlreadyCalculated == true`. Нужно отдельно хранить каталожную и рассчитанную цены либо инвалидировать расчёт при изменении исходных данных.

### R03. Offline-бронь теряет выбранный договор

Код: [создание pricingTerms только online](</Users/a123/a123-dev/lima/lib/features/visits/presentation/view_models/pharmacy_order_view_model.dart:348>), [сериализация договора](</Users/a123/a123-dev/lima/lib/features/visits/data/mappers/pharmacy_order_draft_mapper.dart:33>).

В offline-ветке `pricingTerms` остаётся `null`, хотя `config` уже содержит выбранные договор, наценку и другие условия. В черновик и `raw_json` они не попадают; восстановить выбор при повторной отправке невозможно. Предоплата и тип покупателя сохраняются отдельно, но это не компенсирует потерю договора.

Тест R03: выбран `contractId = 7`, после сохранения в payload значение отсутствует. Выбор пользователя следует сохранять независимо от доступности online-расчёта.

### R02. При оформлении корзины используется устаревший идентификатор остатка

Код: [формирование строки заказа](</Users/a123/a123-dev/lima/lib/features/visits/presentation/view_models/pharmacy_order_view_model.dart:303>).

После обновления каталога `state.drugs` содержит актуальные идентификаторы, но `buildSelectedLines()` отдаёт приоритет `currentStockId` и `bindingDrugId` из старого снимка корзины. Это оставляет путь повторного получения ошибки «товар не найден». Кроме того, цена/серия берутся из одного объекта, а идентификаторы — из другого.

Тест R02: актуальный stock ID в состоянии — 999, в сформированной строке — прежний 90. Нужна единая проверенная связка товара, партии, цены и идентификаторов; при недоступности прежней партии требуется явное повторное разрешение выбора.

### R04. Заказ отправляется частично без предварительного согласования

Код: [проверка только полностью пустого заказа](</Users/a123/a123-dev/lima/lib/features/visits/presentation/view_models/pharmacy_order_view_model.dart:337>), [уведомление после отправки и очистка корзины](</Users/a123/a123-dev/lima/lib/features/visits/screens/new_bron_screen.dart:313>).

Невалидные позиции исключаются, но наличие хотя бы одной валидной позволяет сохранить/отправить уменьшенный заказ. Уведомление об исключении появляется уже после операции, а очистка удаляет всю группу корзины, включая неотправленные позиции.

Тест R04: из двух выбранных товаров один без binding; вместо `invalidLines` получен `queued` с неполным заказом. До сохранения/отправки нужно блокировать ошибочные строки или получать согласие на частичный заказ; исключённые позиции нельзя терять из корзины.

### R05. Отложенное начало рабочего дня не блокирует его окончание

Код: [выбор только готовых событий](</Users/a123/a123-dev/lima/lib/core/db/local_database.dart:1567>), [обход очереди](</Users/a123/a123-dev/lima/lib/core/services/pending_workday_sync_service.dart:66>).

Фильтр `readyOnly` убирает из выборки начало дня с будущим `next_retry_at`. Более позднее событие окончания остаётся доступным и уходит первым. После него `sync()` возвращает `true`, разрешая также обычные мутации, хотя начало дня ещё не отправлено.

Тест R05: начало отложено на час, окончание готово; API получил `end`, результат `drained = true`. Следует читать очередь по порядку и останавливаться на первом ещё не готовом неприпаркованном событии, а не исключать его до обхода.

### R06. HTTP 401/429 необратимо удаляют план из очереди

Код: [обработка HTTP-ошибок](</Users/a123/a123-dev/lima/lib/core/services/pending_plan_sync_service.dart:84>).

Любой ответ 4xx приводит к `deletePendingPlan()`. Поэтому истечение авторизации или ограничение частоты запросов теряет отправку плана вместо повтора. Локальная карточка может остаться, создавая впечатление сохранённого плана, который уже не будет отправлен.

Два теста R06-401/R06-429: после ошибки очередь пуста вместо сохранения одной записи. Ошибки авторизации и временные ограничения нужно оставлять для повторной отправки; постоянные ошибки валидации — сохранять с диагностикой, а не молча удалять.

### R08. Полное обновление справочников удаляет локальные планы с неотправленными действиями

Код: [удаление planned_visits](</Users/a123/a123-dev/lima/lib/core/db/local_database.dart:1823>), [восстановление только серверных планов](</Users/a123/a123-dev/lima/lib/core/db/local_database.dart:1918>), [pull при оставшихся pending](</Users/a123/a123-dev/lima/lib/core/providers/sync_provider.dart:1127>).

`replaceRemoteSnapshotPreservingUnsynced()` сохраняет несинхронизированные визиты и временные организации/врачей, но не локальные планы. После очистки `planned_visits` очередь `pending_plans` остаётся со ссылкой `local_plan_id` на отсутствующую запись. Сценарий достижим, если отправка плана временно не удалась, а загрузка справочников продолжилась.

Тест R08: после полного seed очередь содержит план, но связанной локальной записи уже нет. Нужно сохранять локальные планы и их идентичность вместе с очередью либо атомарно переустанавливать связи при слиянии.

## P2 — последующие исправления

### R09. Полное обновление теряет ссылки на уже скачанные материалы

Код: [повторная вставка материалов](</Users/a123/a123-dev/lima/lib/core/db/local_database.dart:1893>), [имя файла по локальному ID](</Users/a123/a123-dev/lima/lib/core/services/material_cache_service.dart:139>).

В отличие от `drugs.image_cached_path`, поле `drug_materials.cached_path` не переносится при замене справочников. Локальные ID также могут измениться, а файловый кэш использует эти ID. При отсутствии другого доступного кэша материал снова потребует сеть, хотя файл уже скачивался; разрыв соединения после обновления метаданных нарушает offline-доступность.

Тест R09: тот же материал после seed имеет `cached_path = null`. Нужен перенос по стабильному ключу материала/URL с проверкой актуальности содержимого, а не зависимость от переиздаваемого SQLite ID.

### R10. История объединяет разные локальные заказы за одну минуту

Код: [ключ дедупликации](</Users/a123/a123-dev/lima/lib/features/visits/data/history_records_mapper.dart:12>).

Когда remote ID ещё нет, ключ состоит из типа, организации и отформатированного времени до минуты. Разные локальные заказы в одну организацию в одну минуту получают одинаковый ключ; один исчезает из отображаемой истории, хотя в БД остаются оба.

Тест R10: заказы в 16:19:01 и 16:19:40 дают одну запись вместо двух. Для локальных записей нужен стабильный local ID; слияние с серверной копией должно опираться на явную связь идентификаторов.

### R11. PNG-спецификация обрезает текст внутри товарных строк

Код: [фиксированная высота строки](</Users/a123/a123-dev/lima/lib/core/services/specification_export_service.dart:370>), [ограничение четырьмя строками](</Users/a123/a123-dev/lima/lib/core/services/specification_export_service.dart:630>).

Название, производитель, серия и срок годности объединены в один текстовый блок с `maxLines: 4`. Если название занимает две и более строк, весь блок уже не помещается. Это отдельная проблема от размера общего изображения: даже при видимых границах таблицы часть данных внутри ячейки не выводится.

Подтверждено статическим чтением renderer; новый golden/render-тест не выполнялся. Нужны измерение высоты текста, динамические высоты строк и тест длинного названия со всеми реквизитами. По одному присланному изображению нельзя установить, было ли оно дополнительно обрезано отправителем.

### R12. Текущий CI останавливается на warning анализатора

Код: [неиспользуемая функция](</Users/a123/a123-dev/lima/lib/core/network/remote_api_service.dart:1252>), [шаг CI](</Users/a123/a123-dev/lima/.github/workflows/ci.yml:21>).
